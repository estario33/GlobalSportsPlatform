# ADR-001: Стиль: укрупнённые доменные сервисы и событийная шина

[← Индекс ADR](README.md)

- **Статус:** принято (на утверждение архитектурным комитетом)
- **Дата:** 2026-10-25
- **Этап регламента:** 2

## Контекст
Нужно обслуживать три разных профиля нагрузки (запись тренировок, лента/уведомления, live-соревнования) силами многих команд на разных языках. Требования: QA-2 и QA-3, ограничение сложности эксплуатации (RSK-16).

## Решение
Система строится из 8–12 доменных сервисов с границами по bounded contexts ([04](../04-conceptual-architecture.md)). Ingestion и Competitions выделены в отдельные сервисы из-за особого профиля. Асинхронный обмен через событийную шину, синхронный — через API Gateway/BFF и gRPC/REST внутри. Каждый сервис владеет своими данными; общих таблиц нет. Дробление сервиса допускается, если выполнено хотя бы одно: независимая нагрузка > 5× соседей, отдельная команда-владелец, разные требования к безопасности.

## Рассмотренные альтернативы
- Монолит и модульный монолит — не масштабируются по профилям нагрузки, единый радиус отказа.
- Мелкие микросервисы (30+) — сложность и риск распределённого монолита.
- Serverless-first — lock-in, противоречит ADR-003; допускается точечно для обработчиков событий.
Матрица оценок: [10.1](../10-architecture-options.md).

## Последствия
+ независимое масштабирование горячих путей; чёткие границы для команд.
− нужна платформа и единые шаблоны сервисов; распределённые транзакции заменяются сагами и outbox (см. [concurrency](../views/14c-concurrency.md)).
Пересмотр: если число сервисов > 15 без явной потребности или > 30% изменений затрагивают ≥ 3 сервиса.

## 3.1 Реестр стейкхолдеров

Влияние (В) и интерес (И): H — высокий, M — средний, L — низкий.

| Стейкхолдер | Интересы | Опасения | В/И | Цели/QA |
|---|---|---|---|---|
| Спонсор (руководство, CMO) | Рост бренда и продаж, окупаемость | Расходы без видимого эффекта, репутационные риски | H/H | BG-1, BG-2 |
| Глобальный маркетинг/бренд | Единый образ бренда, данные об аудитории | Потеря контроля над образом из-за UGC | H/H | BG-1, BG-2 |
| Региональный маркетинг | Локальные акции, языки, культурные особенности | Централизованный продукт «не про нас» | M/H | FR-PM-02, QA-3 |
| Владельцы магазинных и спортивных приложений компании | Трафик и продажи, минимум вмешательства в свои системы | Нагрузка на их API, дублирование функций, зависимость от нового приложения | H/M | R10, NFR-INT |
| Продукт-менеджмент | Быстрый time-to-market, метрики вовлечения | Перегруженный scope, архитектурные ограничения | H/H | BG-3 |
| Пользователи-любители | Простота, мотивация, прогресс | Сложность, спам-уведомления, слежка | M/H | BG-3, QA-1 |
| Продвинутые спортсмены | Точные метрики, устройства, аналитика | Неточные данные, закрытость устройств | M/H | R9, O3 |
| Родители и дети | Безопасность, контроль | Контакты с посторонними, трекинг | M/H | O5, FR-ID-03 |
| Организаторы групп/соревнований | Инструменты, масштаб, честность | Читеры, сбои в день старта | M/M | O2, FR-CP |
| Юридический отдел и DPO | Соответствие GDPR/CCPA/LGPD/PIPL и т.д. | Штрафы, блокировки рынков | H/H | BG-4, QA-1 |
| Информационная безопасность (CISO) | Модель угроз, контроль доступа, аудит | Утечка геоданных, взлом аккаунтов | H/H | QA-1 |
| Архитектурный комитет | Согласованность с ландшафтом, контроль рисков | Дорогое «зоопарк»-решение, недодуманность | H/H | все |
| Платформа/облачные команды, FinOps | Стандарты, управляемые затраты | Рост затрат, vendor lock-in | M/H | QA-2, TCO |
| Команды разработки (много стран/языков) | Чёткие границы, свобода выбора технологий | Монолит-узкое горло, плохая документация | M/H | QA-3 |
| Поддержка и модерация | Инструменты, понятные процессы | Лавина жалоб, отсутствие инструментов | L/M | FR-AD-02 |
| Производители устройств, Apple/Google | Использование их API по правилам | Нарушение правил стора и политик данных | H/L | R9, O4 |
| Регуляторы и стороны платёжных/рекламных политик | Соблюдение закона | — | H/L | BG-4 |
| Бренд-амбассадоры и профессиональные спортсмены | Контроль использования их данных и имиджа | Неавторизованное использование данных | M/L | FR-AN-04 |

## 3.2 Конфликты интересов и как они разрешаются

| Конфликт | Стороны | Подход |
|---|---|---|
| Таргетинг vs приватность | Маркетинг ↔ DPO/пользователи | Таргетинг только по данным с согласием; приватность по умолчанию; метрики opt-in в BG-4 |
| Единый бренд vs локальность | Глобальный ↔ региональный маркетинг | Единый движок промо + региональные политики/шаблоны, согласование через роли и ревью |
| Скорость vs зрелость архитектуры | Продукт ↔ Архитектурный комитет | Поэтапный план: MVP с ограниченным scope, критичные компоненты (идентичность, ingest) проектируются «на вырост» |
| Открытые сообщества vs безопасность детей | Продукт ↔ Родители/DPO | Закрытая модель по умолчанию для несовершеннолетних, модерация, возможное отложенное включение |
| Интеграции vs автономия магазинных систем | Наше приложение ↔ владельцы существующих систем | Anti-Corruption Layer, кэш, rate limits, read-only на старте |
| Единая облачная платформа vs «лучший провайдер на задачу» | Платформа ↔ команды | Переносимая платформа (K8s + переносимые примитивы), провайдер на ячейку |

## 3.3 План взаимодействия

- **Высокое влияние/высокий интерес** (спонсор, маркетинг, DPO, CISO, комитет): регулярные ревью архитектуры, включение в приёмку каждого этапа.
- **Высокое влияние/ниже интерес** (владельцы магазинных систем, Apple/Google): ранние соглашения об API и нагрузке, мониторинг изменений правил платформ.
- **Остальные:** участие через бета-программы, гайды для разработчиков, обратная связь через поддержку и исследования.

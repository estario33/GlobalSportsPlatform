# 10. Архитектурные опции и обоснование выбора

[← НФТ](09-nfr.md) · [Оглавление](../README.md)

Методика: для каждого значимого решения перечислены альтернативы, критерии берутся из [QA](08-quality-attributes.md), [целей](01-business-goals.md) и [НФТ](09-nfr.md), выбор фиксируется и позже оформляется как ADR (этап 2; кандидаты — в разделе 10.8).

## 10.1 Стиль архитектуры (решение D1)

Критерии и веса: безопасность/изоляция (QA-1) 0,30; масштабируемость (QA-2) 0,25; модифицируемость (QA-3) 0,25; реализуемость — сроки, сложность, стоимость, сходимость 0,20. Оценки 1–5 — экспертные.

| Опция | Безоп. | Масшт. | Модиф. | Реализ. | Итого | Комментарий |
|---|---|---|---|---|---|---|
| A1. Единый монолит | 3 | 2 | 2 | 5 | 2,90 | Быстро стартует, но разные профили нагрузки (ingest, live, лента) не масштабировать независимо; один радиус отказа |
| A2. Модульный монолит (на ячейку) | 3 | 3 | 3 | 4 | 3,20 | Хороший старт, но много команд на разных языках и тяжёлые профили ingest/live упрутся в единый деплой |
| A3. Мелкие микросервисы (30+) | 4 | 5 | 4 | 2 | 3,85 | Лучшая гибкость, но высокая эксплуатационная сложность, риск «распределённого монолита» при многоязычных командах (RSK-16) |
| **A4. Укрупнённые доменные сервисы (8–12) + событийная шина, ingest и real-time выделены** | 4 | 4 | 4 | 4 | **4,00** | Баланс; границы совпадают с доменами из [4.4](04-conceptual-architecture.md); дробление по измеренной необходимости |
| A5. Serverless-first | 3 | 5 | 3 | 3 | 3,50 | Эластично, но противоречит облачной нейтральности (RSK-15) и сложнее для долгих стримов; допустимо точечно (обработка событий, нагрузочные пики) |

**Выбор: A4.** Чувствительность: при смещении весов в сторону масштабируемости (0,40) A3 обгоняет A4 незначительно (4,10 vs 4,00). Риск снижаем тем, что самые «горячие» пути (Ingestion, Competitions) уже выделены, а критерии выделения новых сервисов зафиксируем в ADR.

## 10.2 Региональная модель данных (D2)

| Опция | Плюсы | Минусы |
|---|---|---|
| B1. Единая глобальная БД и кластер | Проще, простая социальная модель | Нарушает резидентность данных, высокая задержка вне региона, единая точка отказа |
| **B2. Региональные ячейки + «домашний регион» пользователя + глобальный Directory без PII** | Соответствует O1/O5; изоляция отказов; рост по регионам | Сложная федерация (друзья из разных ячеек), путешественники — отдельный путь |
| B3. Полностью независимые инстансы по странам без федерации | Максимальная изоляция | Рвётся глобальное сообщество, дубли разработки и операций |

**Выбор: B2.** Федерацию делаем минимальной: общий псевдоним, публичный профиль, запросы дружбы; всё остальное остаётся в ячейке. Риск RSK-12 снижается этапным запуском (1 → 3 ячейки).

## 10.3 Облачная стратегия (D3)

| Опция | Плюсы | Минусы |
|---|---|---|
| C1. Один облачный провайдер для всего | Простота, скидки | Нет присутствия везде, где нужны ячейки; сильный lock-in; противоречит практике компании |
| C2. Каждый сервис — «лучшее у любого провайдера» | Максимум возможностей на задачу | Зоопарк, межоблачный трафик, сложность безопасности и эксплуатации |
| **C3. Единая платформа (K8s, IaC, переносимые примитивы) + провайдер выбирается на ячейку; разрешённый перечень managed-сервисов** | Баланс переносимости и скорости; соответствует регионам | Часть уникальных сервисов недоступна; нужна платформенная команда |

**Выбор: C3.** Каждая ячейка живёт у одного провайдера; сервис не размазывается между облаками.

## 10.4 Хранение данных (D4)

| Опция | Комментарий |
|---|---|
| E1. Одна реляционная БД на всё | Не подходит для телеметрии и лидербордов |
| E2. Полиглот без ограничений | Рост сложности |
| **E3. Ограниченный полиглот:** реляционная БД (Postgres-совместимая, в т.ч. гео-расширения) для оперативных данных; объектное хранилище для сырых треков; Redis-совместимый кэш/лидерборды; озеро данных/колоночное хранилище для аналитики | Каждый тип данных в подходящем месте, ≤ 4 технологий |

Отдельная графовая БД на старте не нужна (социальный граф помещается в реляционную с индексами); пересмотреть при росте.

## 10.5 Клиент (D5)

| Опция | Плюсы | Минусы |
|---|---|---|
| F1. Кроссплатформа целиком (Flutter/RN) | Один код UI | Риски в фоновой записи, BLE и Health API (RSK-10) |
| F2. PWA | Дёшево | Невозможна надёжная фоновая запись |
| **F3. Нативные iOS/Android для записи, синхронизации, BLE, Health; общий протокол синхронизации; UI — нативный в MVP, пересмотр после фазы 1** | Максимальная надёжность ключевого сценария SC-1 | Две кодовые базы; компенсируем общими контрактами и тестами |

## 10.6 Режим работы live-соревнований (D6)

| Опция | Комментарий |
|---|---|
| G1. Постоянные WebSocket для всех участников | Дорого на 500 тыс. соединений, сложность при деградации |
| G2. Опрос клиентом | Лишняя нагрузка, неравномерная |
| **G3. Пакетная отправка данных (10–30 с) + лидерборд в памяти + снапшоты через CDN/кэш раз в 5 с; WebSocket только для небольших закрытых событий** | Предсказуемая нагрузка, дешевле, масштабируемо |

## 10.7 Build vs Buy для ключевых функций (D7)

| Функция | Решение | Причина |
|---|---|---|
| Социальные группы и лента | **Build** | Ядро BG-1, приватность и контроль данных; готовые SaaS нарушают резидентность |
| Push-доставка | **Buy** (APNs/FCM, e-mail провайдеры) | Коммодити |
| Промо-движок | **Build минимально + интеграция с маркетинговыми платформами компании** (A-3) | Правила на согласиях и инвентаре уникальны; рассылка — у существующих платформ |
| Каталог и покупка | **Reuse** существующих систем через ACL | Non-goal — собственная корзина |
| Чат | **Отложить** | Не критично для MVP, высокие риски модерации |
| Мониторинг/CI/CD | **Reuse** корпоративной платформы | Единые стандарты |

## 10.9 Итог

Выбрана архитектура **«региональные ячейки из укрупнённых доменных сервисов на общей облачно-нейтральной платформе, с offline-first нативным клиентом и выделенными путями ingest и real-time»**. Она минимизирует главные риски (RSK-03, RSK-10, RSK-11, RSK-12, RSK-16) и отвечает на три основных атрибута качества.
